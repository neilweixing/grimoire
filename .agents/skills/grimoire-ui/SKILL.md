# Grimoire UI

Preserve Grimoire's warm light appearance and One Dark-inspired dark appearance and make equivalent controls behave and look alike across modules. Use ChatGPT as a reference for readable conversation text and clear interface hierarchy, while following the concrete Grimoire baselines below.

## Read before implementing

Read [the design system](references/design-system.md) before creating or restyling UI. It defines the color roles, typography, chat rendering, spacing, geometry, state matrix, and verification criteria. The numbers are project baselines, not a claim about ChatGPT's official design tokens.

All implementation paths in this Skill are relative to the repository root:

- `apps/grimoire-web/src/styles.css`: current runtime theme, shared classes, responsive rules, and reduced motion.
- `apps/grimoire-web/src/select.tsx`: shared searchable select, custom values, keyboard handling, and top-layer popups.
- `apps/grimoire-web/src/menu.tsx`: shared Radix cascading menus, keyboard search, portal positioning, and viewport collision handling.
- `apps/grimoire-web/src/confirm-dialog.tsx`: confirmation lifecycle, initial focus, cancellation, pending state, and errors.
- `apps/grimoire-web/src/model-picker.tsx`, `execution-controls.tsx`, and `project-actions.tsx`: model, permission, and project menus.
- `apps/grimoire-web/src/thread.tsx`: conversation structure and Markdown rendering.
- `apps/grimoire-web/src/composer-skill-input.tsx` and `composer-skills.tsx`: native assistant-ui Skill completion, shared enabled Skills, and visual command highlighting.
- `apps/grimoire-web/src/provider-form.tsx`, `settings.tsx`, and `integration-settings.tsx`: forms and settings patterns.
- `apps/grimoire-web/src/i18n.tsx`: English and Simplified Chinese strings.

Inspect the owning component and a matching shared component before editing. Existing CSS includes legacy small text and one-off dimensions; do not turn every current value into a new convention. The reference defines targets for new or modified UI. It does not imply that a documentation update has already migrated the runtime styles.

## Apply the system

1. Identify the component's role: conversation content, navigation, settings row, form field, menu, dialog, or supplementary metadata.
2. Choose its typography, spacing, surface, and density from the reference. A field, its trigger, and the corresponding menu must use compatible text sizing.
3. Extend shared components and classes. Consolidate a recurring value in the owning shared style rather than appending another override at the end of `styles.css`.
4. Implement the states relevant to that component. Preserve its data flow, validation, and backend boundaries.
5. Review the result next to an existing equivalent, using both languages and a constrained viewport when UI has changed.

When a touched component differs from the baseline, align the affected component family within the requested scope. Preserve established exceptions such as message-bubble shape, compact composer controls, the update action, and the desktop title bar. An explicit user instruction takes precedence; update the relevant shared rule and this guide when the user intentionally changes the design system.

## Shared interaction patterns

Use `Select` for flat form choices and `menu.tsx` for cascading composer actions. The composer model picker uses a single popup with Model and Reasoning effort entries. Model opens a page grouped by provider, listing only configured models without a search field. Reasoning effort opens the selected model's supported levels in the same popup. Do not add a Back button. Selection, outside click, and Escape dismiss the popup; reopening starts at the main page. Focus the selected or first enabled option when entering a page and restore focus to the trigger on dismissal. Skills retain their searchable side submenu, with viewport collision handling. Keep Arrow-key navigation, outside-click/focus dismissal, and focus restoration intact. Provider settings may retain model search; short lists such as language use a simple choice list. Custom model IDs remain editable in provider settings when discovery is unavailable. Connections support multiple configured models with independent capabilities and a default. Defaults come from Pi or explicit endpoint metadata. Reasoning-level tests use real short Pi requests after a cost-aware confirmation, report acceptance separately from proven support, and check accepted levels in the draft automatically without saving. Do not render per-level test results or an explanatory result panel; reflect test outcomes through the draft checkboxes only. Place the test action next to Thinking depth; retain prior choices for inconclusive levels and preserve the existing selection if no level is accepted. Include Max when supported; do not maintain a separate six-level limit. The composer only lists configured models and filters reasoning choices to the selected model's supported levels. Extend existing menus for action groups; do not introduce another visual menu system or system-native select.

Support keyboard navigation, selection, Escape, outside-click dismissal, disabled options, visible focus, and focus restoration. Dropdowns inside dialogs stay interactive in the top layer, fit the viewport, and handle ancestor scrolling without clipping or moving the page unexpectedly.

Reuse `ConfirmDialog` for project/chat deletion and permission escalation. Use an action-appropriate icon and tone, concrete consequences, and explicit actions. Focus Cancel initially, prevent duplicate submissions while pending, display failures in the dialog, and close after success. Do not use `window.confirm` or `window.alert` for application confirmations. Keep full-access acknowledgement and backend permission checks intact. Permission labels are Read only, Ask for approval (the default), and Full access; the middle mode allows project work and network requests directly and requests approval for project-external edits and external tools. Read-only mode permits OS-sandboxed read-only commands. Built-in browser operations retain their separately requested exemption.

## Product conventions

- General preferences (language, appearance, and browser certificate trust) persist in `~/.grimoire/config/preferences.json` through the preferences API; browser storage is not their source of truth. Use shared theme tokens with light-mode fallbacks and verify chat, code, settings, menus, cards, scrollbars, and native surfaces in both appearances.
- Desktop General settings retain an explicit Quit Grimoire action beside the version. Use the validated main-frame-only app bridge and normal application shutdown, preserving close-to-minimize and updater cleanup. Omit the action in web mode.
- Desktop General settings expose Clear cache under Storage, with pending, success, and retryable error feedback. Clear HTTP and generated code caches while keeping cookies and website storage. The adjacent automatic cleanup row uses a switch and integer day counter, defaults to 7 days, persists 0 for off, and preserves 16px spacing between rows. Save a valid day counter on blur or Enter and keep validation errors next to the control. Chat deletion includes only the owning chat's browser data and uses the existing confirmation dialog; do not add an extra confirmation for routine cache cleanup.
- General settings rows use text labels and controls without leading decorative icons. Follow the settings spacing baseline in the design system; adjacent outlined controls must remain visibly separated in both appearances and languages.
- Align the Projects heading add action with the trailing New chat icon in project rows, using the same horizontal target width and right inset. Project folders keep neutral selection styling; their label, More, and New chat actions share one full-row hover/focus background, without separate button fills. Selected chats retain their full-width highlight. Titles of chats nested under a project align with the folder name, while the background and click target remain full width. Long sidebar names stay on one line with an ellipsis. Project chat rows expose a trailing delete action on hover or keyboard focus (always visible on touch devices), sharing the row background and the existing chat-deletion confirmation flow.
- Copy actions use `writeClipboardText` from `apps/grimoire-web/src/clipboard.ts`. Desktop writes go through the validated write-only bridge; web mode retains the browser Clipboard API. Message controls use assistant-ui's native `useActionBarCopy` with that writer, preserving source Markdown and copied feedback. Pass explicit final-answer text for assistant copies, excluding collapsed progress and reasoning. User copies omit attachment metadata and native Skill injection, using persisted pre-expansion `originalText` for native Skill messages, including queued turns. Use the original query suffix to locate the injected Skill boundary; XML examples in the query or Skill body must not truncate the copied text or leak injected instructions into the visible question. Older sessions without source metadata retain a best-effort command reconstruction fallback. Never solve copy failures by granting embedded pages clipboard access.
- User messages align right with a uniform 18px radius on all four bubble corners. Omit speaker names, initials, and avatars from conversation rows. Show the original send time and a copy action below user bubbles, aligned right; copy source text rather than rendered HTML or metadata. Completed assistant answers show their persisted message time next to Copy. Both roles reuse the 12px / 18px time treatment; never substitute the current render time.
- Skill autocomplete uses assistant-ui TriggerPopover primitives and its Directive insertion behavior. A leading `/skill` searches enabled Skills shared with the plus menu; Enter/Tab or a click completes plain `/skill:name` text without submitting. Preserve following task text, IME behavior, caret position, and native text copying. Highlight recognized enabled Skill prefixes with the existing warm accent and no padding or font changes that would misalign the textarea caret; the visual layer stays hidden from assistive technology and synchronized with scrolling.
- Base composer density on the actual chat pane width with container queries. Below 640px, metrics show three focusable icons whose hover/focus tooltips show only the original one-line metric values, without explanatory text or model names; below 520px, the permission trigger keeps only its mode icon. Restore labels automatically when the pane grows, keep model/send controls usable, and share the preferred 360px chat minimum between drawer CSS and drag limits. Tooltips must stay inside the chat pane so native browser views cannot cover them.
- The composer plus menu contains only Add local files and Use Skill. Its trigger has a transparent circular target with a subtle circular hover/open treatment. Selecting a Skill or file closes the menu; keep the assistant-ui attachment action mounted outside the menu portal so closing does not cancel the system file chooser. Reuse assistant-ui attachment primitives for pending file cards and removal. Selecting files or Skills updates the draft without sending or uploading; files upload only on Send. Omit internal attachment paths from user bubbles, copy text, queue previews, and navigation. Queued attachments taken back for editing return as file cards.
- During an active run, ordinary submission and Enter enqueue a native Pi follow-up; Insert now uses native steering. Display the server's queues in a compact, integrated area at the top of the composer, without a second browser queue. Use ComposerPrimitive.Queue for follow-ups. Edit takes back the actual pending queue through Pi, appends any existing draft without losing text, and returns focus to the input; multiple queued messages are edited together. Do not wire unsupported per-item edit/remove primitives to the react-pi adapter. Keep the ordinary placeholder during execution; omit supplemental-input instructions. Preserve the native stop/clear behavior and do not imply that steering forcibly interrupts a running tool.
- Multi-turn chat navigation sits at the viewport's right edge, leaving the composer and metrics intact. One mark represents one user turn; highlight the visible turn, support keyboard activation, and preview only its question and final answer, excluding tool payloads, progress, and reasoning. Use the existing warm surface and muted typography for previews.
- Tool summaries show the command or meaningful operation target without a native title tooltip containing the full command or output. Leading icons and disclosure chevrons must not shrink when command text is long; truncate the text instead. Long content is available only after expansion; shared selects use short label tooltips rather than entire descriptions. Expanded details show readable input, output, and an explicit execution state; use the terminal-style pattern in the design system.
- Keep one collapsed activity trace per assistant run, including reasoning, tools, skill reads, and intermediate progress. A completed trace uses its text label and disclosure chevron without a leading success icon; reserve state icons for running, approval waiting, and failures. Stream the final answer outside it. Auto-collapse at answer/completion transitions; preserve a subsequent manual expansion across token updates. Pending approval controls remain visible outside the trace.
- Skills settings show the discovered list, per-Skill switches, and Reload. Show each Skill name without an adjacent `/skill:name` command label. Do not reintroduce a global loading switch or extra-directory form without a new request.
- Plugin discovery places tabs and a bounded search field in a wrapping toolbar. Keep the search icon inside the field and its focus border inside the control so scroll containers cannot clip it. Display catalog results in responsive cards with package names, versions, and explicit install actions; installed packages retain their list controls. Use Pi's native update check when opening the installed tab and show a per-package Update action, respecting exact version pins, ranges, and offline mode; never download or install during a check. Keep failed checks retryable and preserve enabled/disabled state after updates.
- Add plugin opens a modal with an npm package name or npmjs.com URL field and a Search action, without a split button or dropdown. Lookup reads metadata only. Trust and install stays disabled until a matching lookup succeeds; editing the field invalidates that result, and stale requests must not re-enable installation. Keep lookup and installation errors in the modal, preserve input for retry, and use Pi for installation.
- Keep status text, captions, and decorative containers only when they help the user make a decision. Use concise action labels rather than implementation descriptions.

## Localization and behavior

Keep code, comments, and documentation in English. Add visible UI strings to both `i18n.tsx` dictionaries. Reasoning-effort field labels are localized; values remain English. Use the same fonts and role sizes in both languages and allow labels to grow without clipping.

Styling must preserve permissions, configuration, session ownership, model capabilities, and asynchronous error handling. Do not add confirmations to actions that currently require none merely to match a dialog example.

## Verification and delivery

Use the reference's review checklist for actual UI changes. Run focused behavior checks and applicable type/format/build checks; do not write tests that merely assert CSS text or copied wording. Report what was verified and any remaining visual exceptions.

For Skill/documentation-only changes, validate the Skill, Markdown formatting, reference links, and agreement with the owning source. Runtime tests and service startup are unnecessary. Respect the user's service state; do not restart stopped services, launch Electron for a web-only task, or publish a release to validate these instructions.
